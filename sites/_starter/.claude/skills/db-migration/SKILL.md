# Database: Drizzle + Neon

Opt-in: most sites have no database (see `.claude/rules/integrations.md`).
Ask for explicit approval before any migration or write query on production.

## Setup when a site gets a database

1. `pnpm add drizzle-orm postgres` and `pnpm add -D drizzle-kit dotenv`.
2. Neon project with two branches: `production` and `development` (a copy of
   production; Neon MCP `create_branch`, parent = production, small compute
   with autosuspend). A branch inherits roles and passwords: its URL is the
   production URL with another endpoint host — no need to print secrets.
3. Env files: `.env` → `DATABASE_URL` of **development**; `.env.live` →
   `DATABASE_URL` of **production**. Both gitignored.
4. `drizzle.config.ts` (reads `.env`) and `drizzle.production.config.ts`:

   ```ts
   import { existsSync, readFileSync } from 'node:fs'
   import { parse } from 'dotenv'
   import { defineConfig } from 'drizzle-kit'
   import base from './drizzle.config'

   if (!existsSync('.env.live')) throw new Error('.env.live is missing.')
   const live = parse(readFileSync('.env.live'))
   if (!live.DATABASE_URL) throw new Error('DATABASE_URL missing in .env.live.')
   export default defineConfig({ ...base, dbCredentials: { url: live.DATABASE_URL } })
   ```
5. Scripts: `"db:generate": "drizzle-kit generate"`,
   `"db:migrate": "drizzle-kit migrate"`,
   `"db:migrate:production": "drizzle-kit migrate --config drizzle.production.config.ts"`.
6. Vercel: `DATABASE_URL` **Production** → production branch, **Preview** →
   development branch (two separate variables, never one for both), plus
   `NUXT_PUBLIC_DATABASE_ENV=development` and `MAIL_REDIRECT_TO` on Preview.
   Changing a variable that spans both environments: `vercel env rm NAME
   preview` removes only that target; to narrow targets precisely, PATCH the
   env id via `vercel api` with `{"target":["production"]}`.

## Conventions

- Schema in `server/database/schema/*.ts`, re-exported from `index.ts`.
- `casing: 'snake_case'` in **both** `drizzle.config.ts` and the client.
- Migrations generated by drizzle-kit; never edit an applied migration.
- **No `db:push`** outside a throwaway branch: it skips the migration history.
- Prefer additive changes (new table, nullable column, column with default):
  the current `main` keeps working while the migration is already live.
  Rename/drop = two releases.

## Steps for a change

1. Change the schema.
2. `pnpm db:generate` — read the SQL. Unexpected `DROP`/`RENAME`? Stop, discuss.
3. `pnpm db:migrate` → development. Check with Neon `describe_table_schema`
   (branch `development`), test the app locally. Risky (data rewrite, drop)?
   First on a throwaway branch of `production`; delete it afterwards (with OK).
4. `pnpm typecheck`, `pnpm build`.
5. Production, only with explicit approval: `pnpm db:migrate:production`.
6. Verify: the last `when` in `meta/_journal.json` equals
   `select max(created_at) from drizzle.__drizzle_migrations;` on `production`.
7. Then ship the code with `release`.

## Pitfalls

- `numeric` comes back as **string**: `Number()` when reading, `.toFixed(2)` when writing.
- `date` columns are `"YYYY-MM-DD"` strings; "today" = the site's local calendar day.
- A table for Better Auth must also go into the `schema` of `drizzleAdapter`,
  keyed by the Better Auth **model name**.
- After dropping a table/column: search `server/`, `app/`, `shared/` for references.
- `development` is a copy of production with real people's data: keep
  `MAIL_REDIRECT_TO` set wherever it is used. Fresh data: Neon
  `reset_from_parent` on `development` (with OK — local test data is lost).
